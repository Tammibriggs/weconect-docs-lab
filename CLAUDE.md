# weConect: API documentation practice project

weConect is a small social app used to practise API documentation end to end: testing, specs, a docs site, CI, and AI integrations. The API and its docs are the focus; the app itself is secondary. The user is learning, so the process matters as much as the result.

## Files

| Path | What it is |
|---|---|
| `api/` | Express backend: MongoDB with Mongoose 5, JWT auth, Socket.io for chat |
| `web/` | React frontend (Create React App) |
| `openapi/weconect-v1.yaml` | The full OpenAPI 3.1 spec (15 endpoints, version 1.0.0), documented as they behave today. App-only endpoints are marked `x-internal: true` |
| `openapi/weconect-public.yaml` | The public spec (10 endpoints), generated by `npm run build:spec`. Never edit it by hand |
| `docs/` | The docs site (Docusaurus 3, `docusaurus-plugin-openapi-docs`), live at https://we-conect-docs.netlify.app/. Netlify builds it with `docs/netlify.toml` |
| `docs/content/reference/` | Reference pages generated from the public spec by `npm run gen` (run by `start` and `build`). Gitignored; never edit |
| `docs/content/quickstart.md` | The quickstart, written by hand. Its HTML comments hold the test's hidden steps |
| `docs/content/guides/` | The how-to guides, written by hand, each tested like the quickstart |
| `tests/docs/` | The docs test: Doc Detective, pinned in its own `package.json` so that `npm install` in the root doesn't download it, and its config, `.doc-detective.json` |
| `docs/src/theme/ResponseExamples/` | Theme override that hides the theme's made-up "Example (auto)" tab |
| `redocly.yaml` | Redocly settings: the `full` and `public` versions and the lint rules |
| `.github/workflows/spec.yml` | CI on every pull request and push to `main`. **Lint the spec:** `npm run lint:spec`, then fails if the committed public spec is out of date. **Contract tests:** `test:capture`, then `test:validate` and `test:coverage` on those captures. **Docs test:** `npm run test:docs` |
| `CHANGELOG.md` | API changes per version |
| `scripts/api-server.mjs` | Starts the API against an in-memory MongoDB; shared by the tests and `npm run dev` |
| `scripts/dev.mjs` | `npm run dev`: the API with sample data, for Postman and the frontend |
| `scripts/start.mjs` | `npm run start:real`: the API and the frontend with the user's real settings and database |
| `tests/cases.mjs` | The live test cases, as data |
| `tests/capture.mjs` | Runs the cases against the API with an in-memory MongoDB and saves each request and response |
| `tests/validate.mjs` | Checks a folder of captures against the spec, including that no response has a field the spec doesn't list |
| `tests/coverage.mjs` | Checks that every response and response field the spec documents appears in a capture |
| `tests/spec.mjs` | Shared by the two checks: loads the spec and the captures, and matches request paths to spec paths |
| `tests/captures/v1/` | Committed evidence: one request and response per case, plus `report.md` |
| `TESTING.md` | Test results, findings (the v2 backlog), and what's untested |
| `PROCESS.md` | The process log: decisions, numbers, problems, and who did what |

## Commands

These are free and safe to run without asking. They use an in-memory database and random secrets.

| Command | What it does |
|---|---|
| `npm run dev` | Runs the API at `localhost:8800` with sample data until Ctrl+C; `-- --empty` skips the sample data |
| `npm run test:capture` | Runs every case; captures go to `tests/runs/<timestamp>/` (gitignored). Fails if port 8800 is in use, for example by `npm run dev` |
| `npm run test:capture -- --out tests/captures/v1` | Refreshes the committed captures |
| `npm run test:validate [folder]` | Checks captures against the spec; exits 1 on any failure |
| `npm run test:coverage [folder]` | Lists documented responses and response fields that no capture shows; exits 1 if there are any |
| `npm run lint:spec` | Lints the full spec, rebuilds the public spec, and lints it. Any warning fails it (`recommended-strict`) |
| `npm run build:spec` | Rebuilds `openapi/weconect-public.yaml` from the full spec |
| `uvx schemathesis run openapi/weconect-public.yaml --url http://localhost:8800 -H "Authorization: Bearer <key>" --workers 1 --continue-on-failure --exclude-checks unsupported_method` | Sends generated requests to `npm run dev`, using the key it prints. By hand only, not in CI; the README lists the failures to expect |
| `npm run test:docs` | For the quickstart and each guide: starts the API with `npm run dev`, runs the page's code with Doc Detective, and checks what it returns. Needs `(cd tests/docs && npm ci --ignore-scripts)` once. Fails if port 8800 is in use. Reports and the code the guides' blocks add up to go to `tests/runs/docs/` |
| `cd docs && npm run build` | Regenerates the reference pages and builds the docs site into `docs/build/`; `npm start` previews it at `localhost:3000` |

Any of these accepts `PORT=<port>` to avoid a server already on 8800, such as `npm run start:real`.

**Never run `npm run start:real` without asking.** It starts the API and the frontend with `api/.env` and `web/.env.local`, so it uses the user's real database and secrets. It's for the user to run.

## Rules

- **Never use a real database or real secrets.** If `api/.env` or `web/.env.local` exists, it holds the user's real MongoDB URL and secrets: don't read, print, or use it.
- **Never commit secrets.** Redact tokens and passwords in captures and examples, as `tests/capture.mjs` does.
- **Document the API as it behaves.** Don't correct its behaviour in the spec. Record problems as findings in `TESTING.md`. When the user asks for a fix, change `api/`, then the spec and `CHANGELOG.md`, and mark the finding fixed with its evidence.
- **Public or internal.** The public endpoints accept API keys (`verifyTokenOrApiKey(scope)` in `api/routes/verifyToken.js`). Endpoints only the app uses accept login tokens only (`verifyToken`) and are marked `x-internal: true` in the spec, along with their tags and any examples about login tokens. A public endpoint lists only `ApiKeyAuth`: Redocly removes an internal security scheme but not references to it, so listing `AccessToken` too would break the public spec.
- **Express 4 and async middleware.** A rejected promise in middleware crashes the server, while a synchronous throw becomes a `500`. Keep code that can throw synchronous, or catch everything in `async` code.
- **Claims need evidence.** Every status code, example, and behaviour in the spec traces to a capture. If something wasn't tested, say so. `npm run test:coverage` checks status codes and fields; it can't check the wording of a description, so when a behaviour changes, also search the spec for text about it. A field in a shared schema shows up in every response that uses it, so when a field applies to only some of them, give those their own schema. `npm run test:validate` fails on a field the spec doesn't list, but not inside a plain `type: object`, so use that only for bodies that really are free-form, such as raw database errors.
- **Update together.** When the API or the spec changes, refresh the captures, then update the spec, `TESTING.md`, `CHANGELOG.md`, and `PROCESS.md`, and run `npm run lint:spec` so the public spec is rebuilt, then `npm run test:validate`, `npm run test:coverage` and `npm run test:docs`. Refreshing the captures gives every user and post a new ID, so update the spec's example IDs and timestamps to the new captures too.
- **The frontend's mock API** (`web/redesign/tools/mock-api.mjs`) reads its own frozen copy of two captures in `web/redesign/tools/fixtures/captures/`, because its IDs are hard-coded. Don't point it back at `tests/captures/v1`.
- **Versions.** 1.0.0 (2026-10-30) is the first published version; 0.1.0 to 0.2.1 weren't published. From 1.0.0 on, a change to documented behaviour is breaking and needs a major version: the planned breaking fixes (findings 8, 27 and 28, the timeline's order, removing like from the public API) wait for 2.0.0. Additions and deprecations are minor versions (like is deprecated in 1.1.0); fixes to behaviour the docs don't promise are patches.
- **Docs site.** The reference pages come from `openapi/weconect-public.yaml`, so change the full spec, run `npm run lint:spec`, then `cd docs && npm run build` to check the site still builds. "Send API Request" stays hidden (`hideSendButton`) until the API is deployed. The sidebar ([`docs/sidebars.js`](docs/sidebars.js)) links to the overview's Authentication, Errors and IDs headings, so if you rename one of them in the spec, change its link too; `onBrokenAnchors: 'throw'` fails the build on a broken one. The "Guides" and "Endpoints" headings are `html` sidebar items made by `heading()` in `docs/sidebars.js`, styled by `.sidebar-section-label` in `docs/src/css/custom.css`; use it for later groups, such as tutorials. Add each new guide to the sidebar by hand. Netlify rebuilds only when `docs/` or the public spec changes, so if the site starts using another file outside `docs/`, add it to the `ignore` command in `docs/netlify.toml`.
- **Docs tests.** `npm run test:docs` tests the quickstart and every guide (the `input` in `tests/docs/.doc-detective.json`). On each page, it runs every `bash` block as written, except blocks marked `testIgnore` after the language (`bash testIgnore`), such as `git clone`, `npm run dev`, and `export` lines with placeholders. It adds every `javascript` block, in order, to the file that the page's "Run the code" section names. A hidden step after the API starts sets that name as `DOCS_FILE` and deletes the files earlier pages made, so a page with tested JavaScript needs that step; without it, the first block fails with a message saying so. After a block, a hidden step in an HTML comment checks the output, which the test saves as `DOCS_OUTPUT`, and saves values the next blocks need, such as `WECONECT_USER_ID`. Write variables as `${NAME}` on the page and in hidden steps: Doc Detective replaces `$NAME` itself before the shell runs, so a quoting mistake a reader would hit still passes (`TESTING.md`, "The docs' commands"). Each page's hidden steps first stop any API an earlier page left running (`closeSurface: api`), then start a fresh one, so every page starts from the sample data a reader has; `before` and `after` in a test comment don't work, because Doc Detective 5.3.1 applies them only to tests in YAML or JSON files. Paths in hidden steps are relative to `tests/docs/` (`relativePathBase: cwd`), and the pages' code runs in `tests/runs/docs/`. When a response changes, update the page's example from a passing run's results in `tests/runs/docs/`. Run Doc Detective by `cd`-ing into `tests/docs/`, not with `npm --prefix`: that drops nvm's Node from `PATH`, so `npm run dev` runs on the system's Node 12 and fails. Doc Detective 5.4 and later need Node 24.22.1; 5.3.1 is pinned because this machine has Node 24.20.0.
- **Guides.** How-to guides go in `docs/content/guides/`, one goal each. Titles start with a bare infinitive, in Google's style ("Find people and follow them"). Code is JavaScript for Node.js with its built-in `fetch`, so it needs no packages. Each step is one part of the goal, with a block a reader can copy on its own: a function that calls `fetch` directly, with the full URL and `process.env.WECONECT_API_KEY`. No setup step, shared constants, or request helper. The last step before "Run the code" puts the functions together. Code blocks have no title: "Run the code" names the file once (`.mjs`, so `await` works outside a function), runs it, and shows the output. Keep lines to 72 characters so the code block doesn't scroll sideways. "Before you begin" links to the quickstart's "Start the API" and "Save your API key" sections instead of repeating them. Examples use the sample data from `scripts/dev.mjs` (alice, who follows bob but not carol); if you change it, update the quickstart's and the guides' examples. Don't use like, which is deprecated in 1.1.0. The reasons are in `PROCESS.md`, entries of 2026-11-22 and 2026-11-23.
- **CI.** The workflow runs the same commands as a local check, so a failure can be reproduced by running the failed step's command. Pin actions to commit SHAs, with the version in a comment. The contract job stays on Ubuntu 24.04 because the tests download MongoDB's build for Ubuntu 22.04. A ruleset on `main` requires the checks, so every change goes through a pull request. Two lint rules are off until they apply: `info-license` until the repo has a license, and `no-server-example.com` until the API is deployed.
- **Ask first** before pushing, deploying, changing `api/` or `web/` behaviour, or anything that costs money or uses an external account.
- **Commits:** no `Co-Authored-By` trailer.
- **Writing style:** Google developer documentation style: plain words, second person, sentence-case headings, short sentences.
- **Audience:** developers who already know how APIs work (intermediate), automating their own weConect account. They can use a terminal and curl, know HTTP methods, headers and status codes, read JSON, and keep a secret in an environment variable: don't explain these; link to MDN's HTTP overview instead. They know nothing about weConect: explain where keys come from and what their scopes allow, which value the next call needs, and weConect's own errors and quirks. While the quickstart runs the API locally, list Git and Node.js as prerequisites and give the commands.
- **Teach as you go.** When you build or change something, explain briefly how it works and why, with file and line references, so the user can explain it later.

## Keeping PROCESS.md up to date

`PROCESS.md` is the user's record for their portfolio, posts, and interviews.

**When to update it:**

- A step or phase finishes.
- A significant decision is made, such as a tool, a design choice, or a change of plan.
- A test run, lint, or check produces new numbers or findings.
- A problem takes real effort to solve, or a claim turns out to be wrong and is corrected.
- Before ending a session that included substantial work.

**Don't log** questions the user asks to understand the code, configuration, tools, or how teams work. Answer them in the chat. If the answer changed something, log the change. If it's a good post idea, add one line to the ideas.

**How to update it:**

- Add a dated entry at the end of the Log, in the same format as the existing entries. Update the Phases table and Key numbers.
- Keep entries to about 15 lines: what changed, the result (one table if there are numbers), and who did what. Leave out explanations of how something works.
- Record the user's reason with each of their decisions, as **Decision (mine):** followed by the reason, in their words where possible. If they haven't given one, ask before logging the decision. If a reason seems weak or rests on something untrue, say so, so they can rethink it.
- Keep "Who did what" honest. Separate what the user did from what Claude Code did. Never credit the user with work Claude Code did, or with checks the user hasn't said they did; ask instead.
- Every number names its source file or command.
- Don't change the results or "Who did what" in old entries. Correct them with a dated note. Explanations can be removed; git history keeps them.
- Add a post or portfolio idea when a step produces a good story.
